# Тестовое задание: Система ставок на события

Этот проект реализует систему ставок на события, состоящую из двух независимых сервисов:

1. **line-provider** — предоставляет информацию о событиях.
2. **bet-maker** — обрабатывает ставки пользователей на события.

## Описание сервисов

### Line-provider
Сервис предоставляет информацию о событиях для ставок. Поддерживаются следующие данные:
- **Уникальный идентификатор события**: строка или число.
- **Коэффициент ставки**: строго положительное число с двумя знаками после запятой.
- **Дедлайн для ставок**: таймстемп, указывающий до какого времени можно сделать ставку.
- **Статус события**:
  - Незавершённое.
  - Завершено выигрышем первой команды.
  - Завершено поражением первой команды.

**Особенности:**
- Информация о событиях хранится в памяти.
- Предоставляется API для динамического создания и обновления событий.

**API:**
- `PUT /event`: Создает событие или обновляет уже существующее и отправляет его в RabbitMQ.
- `GET /event/{event_id}`: Возвращает событие по его event_id:
  - `event_id`: уникальный идентификатор события.

### Bet-maker
Сервис позволяет:
- Принимать ставки от пользователей на события.
- Получать информацию о событиях из `line-provider`.
- Определять статус ставки (выигрыш, проигрыш или ожидание).

**API:**
- `GET /bet/events`: Возвращает список событий, доступных для ставок.
- `POST /bet`: Совершает ставку. Запрос должен содержать:
  - `event_id`: уникальный идентификатор события.
  - `amount`: сумма ставки (строго положительное число с двумя знаками после запятой).
- `GET /bet`: Возвращает историю всех ставок.

## Требования

- Python 3.10+
- FastAPI
- Асинхронное взаимодействие между сервисами.
- Докеризированные сервисы с поддержкой `docker-compose`.

## Установка и запуск

1. ### Клонируйте репозиторий:
   ```bash
   git clone <repository_url>
   cd <repository_directory>```
2. ### Убедитесь, что установлен Docker и Docker Compose.
3. ### Перейдите в корневую директорию проекта, где находится папка docker:
```bash
cd docker/
```
4. ### Создание файлов ```.env``` на основе ```.env.local```:
    Для каждого подкаталога в папке docker вам нужно будет создать файл ```.env``` на основе существующего ```.env.local```.

    Выполните следующие шаги для каждого подкаталога:
- Перейдите в подкаталог (например, ```bet_maker```):
```bash
cd bet_maker
```
- Создайте файл ```.env```, скопировав содержимое из ```.env.local``` (подойдет для локального запуска):
```bash
cp .env.local .env
```
- Повторите эти шаги для всех остальных подкаталогов (```line_provider```, ```postgres```, ```rabbitmq```):
```bash
cd ../line_provider
cp .env.local .env

cd ../postgres
cp .env.local .env

cd ../rabbitmq
cp .env.local .env
```
5. ### Запустите сервисы:
```bash
make up
```
6. ### Осуществите тестирование API:
    Используйте интерактивную документацию Swagger, доступную по следующим адресам:
- Для ```line-provider```: http://localhost:8000/docs
- Для ```bet-maker```: http://localhost:8080/docs

## Что можно улучшить

### Вынесение общих модулей в отдельный репозиторий:
- Выделить общие модули, такие как для работы с RabbitMQ и логгированием, в отдельный репозиторий.
- Такой подход обеспечит консистентность и упростит обновление и поддержку общих решений в нескольких сервисах.

---

### Улучшение эндпоинтов:
- Разделить существующий эндпоинт с логикой для создания и обновления ивентов:
  ```bash
  curl -X 'PUT' \
    'http://0.0.0.0:8000/event'
  ```
    на два отдельных эндпоинта:
- **POST /event**: для создания новых ивентов.
- **PUT /event/{event_id}**: для обновления существующих ивентов.

#### Обоснование:
Разделение операций на два эндпоинта позволяет лучше соблюдать принципы REST, упрощает понимание и поддержку API. Это предотвращает ситуации, когда одна операция влияет на другую, улучшая читаемость и масштабируемость кода.

---

### Разделение логики эндпоинтов на слои:

1. **Слой обработки ошибок и логгирования**:
    - Централизованная обработка исключений.
    - Логирование событий, ошибок и важных операций.

2. **Бизнес-логика**:
    - Содержит правила работы приложения, например, создание или обновление ивентов.

3. **Слой доступа к данным**:
    - Отвечает за взаимодействие с базой данных или другими источниками данных.

#### Обоснование:
Такое разделение улучшает читаемость и тестируемость кода. Каждый слой отвечает за конкретную задачу, что упрощает:
- Отладку.
- Тестирование.
- Внесение изменений.
